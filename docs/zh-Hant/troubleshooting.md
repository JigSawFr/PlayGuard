# 疑難排解

重新取得被鎖住的主機的控制權、回報錯誤，以及開發者模式。返回 [README](../../README.md)。

## 被鎖在外面？

PlayGuard 只能看到它所執行的那個系統的家長監護：**emuMMC 和 sysMMC 各有各的設定**（在其中一邊刪除的PIN碼，在另一邊仍然存在）。請在每個需要處理的系統上各執行一次。

### 二手主機

你知道PIN碼，但前一位主人的手機應用程式仍然連動著（解除連動失敗，或恢復原廠設定時要求輸入他的帳號）。

*PIN碼 › 解除手機應用程式的連動*，接著，如果完全不想要家長監護，再選*刪除所有家長監護設定*。兩者都能離線使用，在 emuMMC 和 sysMMC 上都可以。

### 忘記PIN碼

*顯示PIN碼*本身就需要輸入PIN碼，所以在這裡幫不上忙。如果已安裝復原 sysmodule（見下文），放入一個 `RESCUE` 檔案後重新啟動：復原畫面會讓你設定新的PIN碼（它絕不會顯示舊的）。如果沒有安裝，*刪除所有家長監護設定*可以讓你從頭開始（會先儲存一份設定備份；備份絕不包含PIN碼）：如果*用PIN碼保護PlayGuard*已開啟（預設為*變更前*），請先把 SD 卡放進電腦，在 `sd:/config/playguard/config.json` 中把 `"pin_lock"` 設為 `"off"`。

### 遊玩時間限制封鎖了一切（0 分鐘上限），又忘了PIN碼

這時 PlayGuard 本身無法啟動。請**事先**安裝選用的復原 sysmodule（`playguard-rescue.zip`）；被鎖住時，在 SD 卡上放一個空的 `config/playguard/RESCUE` 檔案再開機——它會解除主機的鎖定，讓 PlayGuard 可以開啟。請見 [`sysmodule/README.md`](../../sysmodule/README.md)（英文）。

這個模組必須跟上 PlayGuard 的版本：每次更新 PlayGuard，都要重新解壓縮該版本的 `playguard-rescue.zip`（或在通知鈴鐺的*復原 sysmodule 不是最新版本*上選*更新*），然後重新啟動主機。舊版模組留下的報告 PlayGuard 無法驗證：這時復原畫面不會提供任何操作，只會說明模組版本較舊；在更新模組之前，再次使用 `RESCUE` 也會得到相同的結果。

### 未改機的主機

PlayGuard 幫不上忙：它需要 Atmosphère。官方的做法是向任天堂客服申請主密鑰（master key）。

## 回報錯誤

發生錯誤時會顯示系統代碼（例如 `0x0001088E`），以及關於它的已知資訊：對於意義已有文件記載的代碼，會說明該怎麼做；其他情況，一份報告會很有幫助。

1. *關於 › 說明與診斷 › 匯出診斷報告*會在 `sd:/config/playguard/logs/reports/` 儲存一個文字檔：韌體、Atmosphère 版本、啟動花了多久、較慢的畫面花了多久（變更紀錄、*所有遊戲*、已安裝遊戲的檢查、會自動重新整理的分頁）、時鐘、儲存空間、序號遮蔽與遊戲修補的狀態、每一次家長監護查詢的原始結果，以及記錄：上次執行如何結束、剩餘的記憶體和 SD 卡空間、最新的當機檔案，以及最後 80 行記錄。**它絕不包含PIN碼或序號。**
2. [開一個 issue](https://github.com/JigSawFr/PlayGuard/issues/new)（英文），並附上這個檔案。

或者，在主機連網時，使用*關於 › 說明與診斷 › 線上傳送報告*（開發者模式下，在診斷報告上按 Ⓧ）傳送報告，同時附上最近的當機報告（PlayGuard 在 `logs/crashes/` 中的最後 3 份，以及 Atmosphère 在 `sd:/atmosphere/crash_reports/` 中過去一週內某個 homebrew 的最後 2 份：其中可能包含其他 homebrew 的當機，傳送前顯示的清單會標明是哪些）、這次及上一次執行的記錄（`logs/sessions/`；記錄太長時：開頭部分和最後 64 KiB）以及除錯檔案（遊玩時間限制區塊的參考、*記錄遊玩時間限制*開啟時遊玩時間記錄的最後部分、變更紀錄的最後 20 筆（不含名稱（遊戲、帳號或設定檔），只保留日期），以及 PlayGuard 的設定），上傳到你 GitHub 帳戶中的一個秘密 gist（報告和每個檔案各自成為一個檔案；未登入時，PlayGuard 會先提議登入；登入後，正下方的 *GitHub 帳戶*可以登出；GitHub 拒絕建立 gist 時，PlayGuard 會提議重新登入）。傳送前，它會清楚說明要傳送哪些內容。接著它會顯示連結和兩個 QR 碼：一個是報告，另一個是錯誤回報表單，已預先填好連結、你的版本、PlayGuard 的啟動方式（在遊戲之上或從相簿；請補上選單）以及系統（sysMMC 或 emuMMC）。任何拿到連結的人都能閱讀報告，直到你在 GitHub 上刪除該 gist 為止；用它開立的錯誤回報是公開的：確認畫面會說明這一點。每個連結都會以網際網路捷徑（`.url`）的形式保存在 `logs/uploads/`，電腦可以用瀏覽器開啟。先前儲存在 `logs/reports/` 中的報告也可以用同樣的方式傳送。

### PlayGuard 在 SD 卡上保存的內容

全部都在 `sd:/config/playguard/logs/`，是電腦可以開啟的純文字：

- `sessions/session_<date>.txt`——**每次執行一個檔案**：PlayGuard 記錄的所有內容（以前只能透過 nxlink 傳到電腦），每一行都有時間和等級（`E` 錯誤、`W` 警告、`I` 資訊），最後一行說明這次執行如何結束：`=== end: clean exit ===`（正常結束），或 `=== end: crash, see logs/crashes/… ===`（當機）。檔案達到 1 MiB 後就不再增加。
- `crashes/crash_<date>.txt`——**每次當機一個檔案**，第一行說明發生了什麼：
  - **CPU 例外**（錯誤的指標、未定義的指令、堆疊溢位）：錯誤的類型和存取的位址、回溯追蹤（backtrace）和暫存器。位址是 `playguard.nro` 中的偏移量（`playguard+0x1a2b3c`）：該建置的連結器對照表（其 CI 執行產生的 `-linker-map` 成品）可以查出對應的函式。之後 PlayGuard 會和以前一樣結束：顯示主機的錯誤畫面，並由 Atmosphère 在 `sd:/atmosphere/crash_reports/` 寫入它自己的報告；
  - **未捕捉的例外**：它的類型和訊息，以及回溯追蹤；
  - **未正常結束的執行**：在下次啟動時發現，也就是上次執行的工作階段檔案沒有結束行時（PlayGuard 無法捕捉的當機、在當住時從 HOME 選單關閉，或主機被關機），附上那次執行的最後 60 行。

  PlayGuard 執行期間捕捉到的當機，其檔案結尾會附上當機前記錄的最後 80 行。
- `reports/`、`uploads/`、`play_timer/`——已儲存的報告、線上傳送的報告的連結、遊玩時間記錄。

*關於 › 說明與診斷*可以設定要保留多少報告、當機檔案、工作階段記錄和連結（每個資料夾分開設定；最新的一份一定會保留）。

## 開發者模式（調查新的韌體）

在*關於 › 版本*上按 Ⓨ 七次；開發者工具會出現在*關於 › 說明與診斷*的最後。它會加入：

- 一個**唯讀**開關——開啟時，應用程式無法變更任何設定：這是調查新韌體的安全方式（韌體畫面會直接提供這個選項）；
- 在畫面上顯示診斷報告（Ⓨ 儲存，Ⓧ 線上傳送），以及從遊玩時間限制分頁匯出報告的捷徑；
- 直接在原處**安裝其他建置**，在修正正式發布前先行測試：最近 20 個版本之一（包括預先發布，會加上標籤）、`main` 最近 20 個提交之一，或從本儲存庫的分支開啟的拉取請求的最新建置（絕不接受來自 fork 的：它的程式碼還沒有經過審查），每一類各在一個分頁中（Ⓛ / Ⓡ 顯示在分頁兩側，用來切換分頁；畫面會開在已安裝建置所屬的分頁，每個分頁都會標出比已安裝建置更新的建置數量）。每個建置都會顯示標題（提交或拉取請求的主旨；提交的完整訊息就是它的說明），下方是標籤：變更的類型（*新功能*、*修正*、*文件*……）和範圍、*不相容*、提交所屬的拉取請求、檢查的結果（*CI 通過*、*CI 失敗*、*CI 進行中*）、預先發布、*已安裝*或*新*；右側是建置的時間和提交。在拉取請求分頁顯示時，按 A 可以反轉排序（最新建置在前，或依編號）。選擇一個建置會先開啟它的頁面：標籤（類型、檢查結果、已安裝或新）、一張資訊卡（建置時間、大小、提交、校驗碼、GitHub 何時刪除它）、**安裝**、**在 GitHub 上查看**（它的頁面以 QR 碼顯示，供手機掃描），接著是版本的說明或拉取請求的描述，依照 GitHub 的 Markdown 排版（標題、清單、核取方塊、程式碼、引言和提示框、表格）。來自 GitHub 的所有內容都以純文字顯示：不會開啟任何連結，不會執行任何 HTML 或腳本，並會移除可能用來偽裝標題的隱形字元（由右至左覆寫、零寬度字元、控制字元、無效的 UTF-8）。登入後，Ⓨ（*搜尋*）可以輸入拉取請求的編號（開啟或已關閉的）或提交（7 到 40 位十六進位數字），找出它的建置，僅限本儲存庫的分支。正式版本不需要任何條件；其他建置是建置工作流程的成品，GitHub 只提供給已登入的使用者：**GitHub 帳戶**會以一組代碼和一個供手機掃描的 QR 碼登入（只要求讀取建置工作流程檔案（Actions）以及建立 gist 的權限，後者用於*線上傳送報告*；除此之外，權杖只能讀取公開內容；權杖保存在 `github_token`，絕不會隨報告傳送，*GitHub 帳戶*也可以登出）。PlayGuard 會下載建置、檢查它（大小、GitHub 記錄的 SHA-256、NRO 標頭），用它取代自己的 `.nro`，然後以新建置重新啟動（只要設有PIN碼，就會先要求輸入）。清單會保留 10 分鐘並立即顯示，同時標明它是多久前取得的（Ⓧ 重新取得）；取得期間，會有一條進度列顯示進度。中斷的下載（網路斷線）會在下次安裝同一個建置時從中斷處繼續。被取代的建置會保留下來（`playguard.nro.previous`）：同一個清單中的**回到上一個建置**可以再把它們換回來。如果從這裡安裝的建置（或透過*更新方式*的*在 PlayGuard 內*更新的版本）在第一個畫面出現前就當機，PlayGuard 下次啟動時，會在載入任何東西之前，以一個簡單的文字畫面提議回到上一個建置（A 回到上一個，B 仍然啟動它），不需要PIN碼，因為當機的可能正是PIN碼畫面本身。其他時候，*回到上一個建置*（見上文）在輸入PIN碼後即可執行。同一個清單隨時都能回到任何一個正式版本；在開發者模式下，*關於 › 版本*會顯示提交。每個畫面的標題列都會在標題旁顯示目前執行的版本：正式版本顯示在灰色標籤中（`1.2.0`），其他建置則顯示在琥珀色標籤中並接著顯示提交，讓測試建置絕不會被誤認為正式版本。成品會在 90 天後過期；
- **比對遊玩時間限制資料區塊**（手機應用程式連動時，也會出現在*PIN碼*中），用來解讀 PlayGuard 還沒有顯示的設定：把原始區塊儲存為參考，在手機應用程式中變更一項設定，再回來——PlayGuard 會列出有變動的數值（可依需要儲存到 `logs/reports/`）。透過手機應用程式設定的每天不同的就寢時間，可以用這個方法確認。請把該檔案附加到 issue 上，或隨報告一起傳送（*線上傳送報告*）。
- **記錄遊玩時間限制**：PlayGuard 開啟期間，每 30 秒把遊玩時間限制回報的內容（剩餘時間、已遊玩時間、原始設定區塊……）寫成一行，存到 `logs/play_timer/log.csv`，這是可以用試算表開啟的檔案；PlayGuard 每次變更後也會立即寫入一行，說明是哪一項變更（最後一欄 `event`），當時鐘移動的幅度超過實際經過的時間時，也會加上註記。讓它開著跨過午夜，或一直開到時間用完，它就能顯示單一報告無法呈現的內容：已遊玩時間何時歸零、主機在快結束時顯示什麼。這個開關會被記住；它只在開發者模式下記錄。目前已知的內容請見 [parental-controls.md](../parental-controls.md)（英文）。
- **清除快取**和**刪除記錄檔**，各自在確認畫面說明檔案數量和佔用空間後執行：快取（`cache/` 以及每個系統的 `nand/<system>/cache/`：遊戲名稱和圖示、活動紀錄的最近數據、建置清單）在需要時會從主機重新讀取；記錄檔包括當機檔案、工作階段記錄（但不含這次執行、仍在寫入中的記錄）、已儲存的報告和遊玩時間記錄，而 `uploads/`（線上傳送的報告的刪除連結）和區塊參考會保留。設定、紀錄、備份、設定檔和匯出檔案絕不會被動到。
