# Pull requests and releases

Part of the [contributor's guide](../../CONTRIBUTING.md).

Releases are automated with [release-please](https://github.com/googleapis/release-please), which reads [conventional commits](https://www.conventionalcommits.org/):

- Give each pull request a conventional title with a scope, the part of the app it changes (`feat(history): …`, `fix(play-timer): …`, `docs(install): …`, `feat(notices)!: …` for a breaking change); CI checks it. release-please sorts each section of the changelog by scope, so a title without one lands apart from the rest.
- **Squash-merge** pull requests, so each one lands as a single commit carrying that title. A plain merge commit makes release-please apply a PR's `BEGIN_COMMIT_OVERRIDE` block to every commit of the PR.
- **Stacked pull requests** (one branched from another's): with squash merges, the second one meets its base's changes again as a single new commit on main, and every file both touched conflicts, though nothing differs. Prefer one pull request with its commits readable one at a time (a refactor first, then the feature), or wait for the first to be merged and start the second from main. When a stack is there anyway: once the first is merged, merge main into the second and keep the second's side of each conflict — main then holds exactly the first's final tree (`git diff <first's last commit> origin/main` shows nothing) — then let GitHub point it at main.
- release-please keeps a `chore(main): release X.Y.Z` PR open; merging it tags the release, as a pre-release, and attaches the `.nro` / `.zip`; once they are there, its page laid out and the site built with it, `pages.yml` publishes it (`releases/latest`, which the app's update check and the site's download links read, stays on the previous release until then). Should the assets job fail, *Actions › build › Run workflow* with the tag (`v1.3.0`) builds it again, and it is published the same way.
- release-please runs with a token of the *PlayGuard Release* GitHub App (variable `RELEASE_APP_ID`, secret `RELEASE_APP_PRIVATE_KEY`; permissions Contents, Pull requests and Issues: write), not `GITHUB_TOKEN`: the app is on the tag ruleset's bypass list, so it can create the `vX.Y.Z` tag, and its pushes to the release PR run the required checks.
- **The release page** is laid out by the release job: a summary (`.github/release-notes/X.Y.Z.md`, merged before the release PR; else, with an `OPENROUTER_API_KEY` secret, one written by a language model), the figures, the commit list folded (users, then contributors), the screens that changed, the install section, the build report, and a discussion. [`.github/release-notes/README.md`](../../.github/release-notes/README.md) says how; *release-page* in Actions does it again for an existing release.

## Development builds

nothing is published for them. The developer tools install the `playguard-<version>-<ref>-<commit>-nro` artifact of a build run (a zip holding `playguard.nro`; the artifacts API only filters by an exact name, so the app lists a few pages of a run's artifacts and keeps that one): main's last commits and the newest run of each open pull request from a branch of this repository; pull requests from forks are left out, as their code is not reviewed yet (`source/util/dev_builds.hpp`, [SECURITY.md](../../SECURITY.md)). GitHub hands artifacts to signed-in users only, hence the GitHub sign-in (device flow, GitHub App client ID in `source/util/github_auth.hpp`; with the Device Flow enabled and token expiry off; the app's only permissions are Actions: read and Gists: write). For a pull request, `PLAYGUARD_COMMIT` makes the app report its head commit, as the artifacts API names the run, and `PLAYGUARD_PR` its number (`app::pr()`): the change history records both for a change a development build made. Every build but a release one (`PLAYGUARD_RELEASE=1`, set for the `vX.Y.Z` tag's build) shows itself as a development build in the header, at the right: an amber **DEV** tag, the version and the commit, where a release shows a plain grey `v1.2.0` (Aurore's `VersionBadge`, from the version and commit `source/activity/screen_hooks.cpp` hands it).

## What a release publishes

Each release also publishes `compat.json` (`tools/gen_compat.py`: the version and the newest checked firmware), which the app's update check reads, plus `build-info.txt` and `SHA256SUMS.txt`. Details in [`packaging/README.md`](../../packaging/README.md). The `.nro`, both `.zip`, `compat.json`, `build-info.txt` and `SHA256SUMS.txt` also carry a [build provenance attestation](https://docs.github.com/actions/security-for-github-actions/using-artifact-attestations): `gh attestation verify playguard.nro -R JigSawFr/PlayGuard` checks that a download was built by this repository's CI.

## Reproducible zips

`make dist` and `make dist-rescue` give every file in the zip the date `SOURCE_DATE_EPOCH` (POSIX seconds; default: the last commit's time, `git log -1 --format=%ct`) and add the files in a fixed order without extra attributes, so the same commit and `.nro` give a byte-identical zip. The deko3d shaders are not compiled at build time (uam does not always give the same bytes): `shaders/` keeps them, with the checksums of the borealis GLSL they come from, and configure stops when that GLSL changes; then rebuild them with `-DPLAYGUARD_UAM=ON`, copy `build/dksh/*.dksh` to `shaders/` and update `shaders/glsl.sha256`. Set `SOURCE_DATE_EPOCH=<seconds>` to rebuild one from another checkout. CI builds the zips twice and compares them on main, for a release and once a week; when they differ, `tools/repro_diff.py` says where (a zip entry, a segment of the `.nro`, a RomFS file, a shader) and the run keeps both builds as an artifact.
