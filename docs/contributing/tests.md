# Tests and CI

Part of the [contributor's guide](../../CONTRIBUTING.md). The host tests themselves: [`tests/README.md`](../../tests/README.md).

- `make test` — host unit tests (`tests/`, see [`tests/README.md`](../../tests/README.md)), including the recovery sysmodule logic (`tests/rescue/`); every suite runs, in parallel, and leaves its output in `build/host-tests/<suite>.log`.
- `tools/desktop_smoke.py <out-dir> [games|gate|errors|rescue|forged|lock|loading|devbuild|update|library|rollback|outside|alarm|sysnotes|cadran|cadranstates|cadranunlocked|cadranlarge|bedtime|forwarders|hbmenu|homebrew]` — clicks through every screen of the desktop build headlessly (needs `DISPLAY`, `xdotool`, ImageMagick) and saves screenshots. Each scenario starts the program anew; with no scenario it opens every tab, the Play timer's editors, the settings backup and the change history. The others:
  - `games` — the rest of that tour, run on its own so CI can run both side by side: a report sent online, *Console › Installed games* with every fix, check and removal, then *Activity › All games* and the PDF export.
  - `gate` — the firmware screen and developer mode on a simulated 24.0.0.
  - `errors` — a failed unlock and an unsettable clock.
  - `rescue` — the recovery screen, then quitting while still unlocked.
  - `forged` — a rescue report the console does not confirm (no action, the lock screen first).
  - `lock` — the lock screen of *Protect PlayGuard with the PIN › To open PlayGuard*.
  - `loading` — the loading screen, the start-up held at its last step.
  - `library` — a large library in *Activity › All games* (its first 50 covers, then *Show every game*, then the list).
  - `devbuild` — signing in to a simulated GitHub and installing a pull request's build in place out of its artifact.
  - `update` — a newer release found at start-up by *Check for updates every day*, postponed, shown again by *About › Check for updates*, then installed in place.
  - `rollback` — a build installed in place whose start never reached its first screen: the start-up offers the build before it, A with the PIN screen left takes nothing back, then A with the PIN takes it back.
  - `alarm` — *Today* and the Play timer tab past the limit while the console only warns.
  - `sysnotes` — the release notes of the firmware, Atmosphère and hekate from *Console*, against a simulated GitHub and switchbrew.
  - `outside` — *Today*'s notices: changes made outside PlayGuard (a play time that started over, the clock, the limits) and, after 90 s on screen, a console that is not counting play time (it takes about two minutes).
  - `cadran` — the boards on top of the tabs: every tab, the child screen and back with the PIN, a day of the week edited with the stick and saved, a restriction level's confirmation and the one a preset's setting changed asks (the level becoming Custom), the text size, the grid of *Start on*, the network clock and a game's screen from its card.
  - `cadranstates` — its Today and Play timer past the limit (a warning only) with changes made outside PlayGuard.
  - `cadranunlocked` — the same two while parental controls are temporarily unlocked (*Turn back on* first, the header's pill saying so), in the light theme (every other scenario draws the default, dark one).
  - `cadranlarge` — Today, the Play timer, Activity, Console, Preferences, About, Help and the child screen with *Preferences › Text size › Larger*, as on a TV.
  - `bedtime` — Today and the child screen at 20:00 with 90 minutes left, the ring counting down to the bedtime at 21:00 instead.
  - `forwarders` — *Console › Forwarders*: one another app made, PlayGuard's own, a homebrew picked and protected with the PIN, then deleted.
  - `hbmenu` — the homebrew menu's lock: the recovery sysmodule's report taken at start-up, its steps (PlayGuard's forwarder, then sphaira found and made protected, its preview, then seen working through its gate), locked with A held on its checklist, the rescue sheet, deleting sphaira refused while locked, unlocked.
  - `homebrew` — Console › Forwarders in use (`PLAYGUARD_SIM_FORWARDERS`): a pause lifted, hours a forwarder never opens, the pause's rule, an icon from the album with its square moved along the screenshot, then its `.nro`'s own again with Y, the rescue sheet's page to print.

  What no simulator can show (the console's HOME menu and PIN screen, Atmosphère reading the lock, the recovery sysmodule at boot): [docs/hardware-test.md](../../docs/hardware-test.md), to go through on a console after a change there.
- `tools/cut_text_check.py <out-dir> [language …]` — starts the desktop build on the tabs in each of the 15 languages, at the normal text size and the larger one, shows every tab, then from *Today* the picker of *Stop for today*, the confirmation of the unlock it needs and that unlock's failure dialog (`PLAYGUARD_SIM_FAIL=unlock`), then the child screen, and fails on any text cut short (drawn with "…"; borealis patch `0008`, `PLAYGUARD_SIM_CUT_TEXT`) that `tests/cut_text/allowed.txt` does not list. About 30 s a language and size; CI's `languages-1` to `languages-5` shards run it, three languages each (needs `DISPLAY` and `xdotool`).
- `tools/visual_check.py` — compares those screenshots with the references, main's own screens of the last run (`tools/visual_refs.py` fetches them, `tests/visual/<scenario>/SCREENS` names the stable screens compared). A screen that changed fails CI unless the pull request announces it on its `Screens:` line; see [`tests/visual/README.md`](../../tests/visual/README.md).
- `tools/smoke_all.py <out-dir> [-j N] [--update]` — runs every smoke scenario (the default one, `smoke`, and each one `desktop_smoke.py` tests for), N at a time (3 by default), each with its own display and D-Bus session (`xvfb-run -a … dbus-run-session`), into `<out-dir>/<scenario>/`; then the visual check of each one that has references, and a summary: each scenario, whether it passed, and the screens that changed. It fails on a failed scenario or a changed screen; `--update` replaces the references of the screens that changed instead. `--dry-run` lists the scenarios and their commands. Needs `make desktop` first.
- `tools/perf_frames.sh <name> [VAR=value …]` — the per-frame cost of one screen of the desktop build, headlessly (same needs as the smoke test, plus `dbus-run-session`): the median and p95 frame time over the steady state, and nanovg's draw calls and triangles once `tools/perf_nanovg_stats.patch` is applied in `extern/borealis` (`git -C extern/borealis apply ../../tools/perf_nanovg_stats.patch`; a local patch, never committed). `PERF_KEYS="Down Right"` presses keys first to reach another screen (xdotool names; Return is A, Escape B), `PERF_THEME=light` runs the light variant. Software GL rasterises on the CPU, so the figures weigh pixels far more than the console's GPU does: compare screens with each other, not with the console.
- `python3 tools/check_resources.py .` — checks the XML layouts and translation catalogs.
- `run-clang-tidy -p build-tidy -quiet "$PWD/source/"` — clang-tidy on PlayGuard's sources with the checks of `.clang-tidy` (the bugprone, cert and performance families; the static analyzer's too, slower), on the desktop build's compile commands made by clang without the precompiled header (`CC=clang CXX=clang++ cmake -B build-tidy -S . -DPLATFORM_DESKTOP=ON -DCMAKE_EXPORT_COMPILE_COMMANDS=ON -DCMAKE_DISABLE_PRECOMPILE_HEADERS=ON`). CI's `clang-tidy` workflow runs it on the files a pull request changes, on every file for a push to main and, with the static analyzer, once a week: a report on the run page and annotations on the pull request, never a failure.
- `python3 tools/check_sources.py .` — checks that `source/ui`, `source/view` and `source/util` include nothing of `activity/` or `tab/` (they reach the screens through `ui/app_hooks.hpp`, or Aurore's `ui::hooks`), that `source/action` includes only the screens its flows open, and that each `source/core/*.c` the console's services are not needed for is in the desktop build's list (`CMakeLists.txt`) and in a host test (`Makefile`).
- `python3 tools/build_site.py <out-dir>` — builds the website (`site/README.md`); CI's `web` workflow builds it with the simulator for every pull request and `pages` publishes it. `node tools/site_screenshots.mjs <simulator> <out-dir>` takes its screenshots in each language from the web simulator.
- `node --test tests/web_page/*.test.js` — the web simulator's page logic (`web/sim_logic.js`).
- `python3 tools/check_web_params.py .` — checks that the web simulator's panel (`web/params.json`) and the table above have every `PLAYGUARD_SIM_*` variable, and that none read once only is marked `live`.

## What CI runs

CI (`.github/workflows/build.yml`) runs all of the above plus the Switch build, the smoke scenarios in parallel shards (the desktop build made once, in `desktop-build`, and handed to them), on every pull request, on every push to main and once a week.

- **main's rules** want a pull request up to date with main before it merges (*Update branch*, then its checks again), so two pull requests green apart cannot break main together. (The workflows also answer GitHub's merge queue, `merge_group`, which only a repository owned by an organization can turn on.)
- **A pull request runs only the jobs its files need** (the `changes` job):
  - documentation, the website, the web simulator's page or other workflows only: the host tests and the resource checks;
  - the host tests' suites only (`tests/` but `tests/visual/` and `tests/cut_text/`): no desktop build or smoke test;
  - the smoke test's references or scripts only: no clang and coverage host tests;
  - nothing the Switch reads (`tests/`, `source/sim/`, the smoke test's scripts): no Switch build.
- **The visual check** compares the screens of `tests/visual/<scenario>/SCREENS` with main's last run's, kept in the Actions cache by main and attached to each release as `playguard-screens.zip`, and fails on a changed screen the pull request did not announce (the simulator keeps the console time and the focus highlight still, so the screens come out the same in every run).
- **The desktop and Switch builds turn PlayGuard's compiler warnings into errors** (`make desktop CMAKE_ARGS=-DPLAYGUARD_WERROR=ON`, `make dist CMAKE_ARGS=-DPLAYGUARD_WERROR=ON`), and a compiler message is annotated on its line of the pull request; the Switch job also fails on a libnx older than 4.12.0 or an `.nro` without libnx's `LNY2` marker (`tools/check_nro.py`), and, outside pull requests (main, a release, the weekly run), checks that a second build gives byte-identical zips; `check_resources.py` warns about sentences a catalog still has in English.
- **Each job writes a summary** on the run page (`tools/ci_summary.py`): what is being built, the suites, the coverage per file, each smoke scenario with its visual check and its time, and for the Switch build the `.nro` size against main's last build, what makes it big (from the linker map: `python3 tools/ci_summary.py map build/borealis.map --nro playguard.nro` shows the same table for a local build), the toolchain and the downloads.
- **A run's artifacts** are named after its build, `playguard-<version>-<ref>-<commit>-<component>` (`1.0.0-pr92-1f0a059`, `1.0.0-main-2bd4996`): `-nro` (the app, what the developer tools download), `-rescue` (the recovery sysmodule, as the zip and the raw `.nsp`), `-hbas` (the Homebrew App Store listing, [`packaging/hb-appstore/`](../../packaging/hb-appstore/README.md), checked against the zip and built by the store's own tool), `-linker-map`, `-screenshots-<shard>` (with a contact sheet per scenario), and on a release build `-sdcard` (the store zip).
- **Only main's builds write the Actions cache** (ccache, the apt packages, the baselines of the coverage and the `.nro` size); a pull request starts from main's and keeps none of its own, which would push main's out of the repository's 10 GB.
- **The runner image is pinned** (`ubuntu-26.04`): the references of the visual check were drawn by its mesa, so moving to the next image is a pull request of its own. The devkitPro image is pinned by digest in `build.yml`; `toolchain-watch.yml` opens an issue once a month when Docker Hub's `latest` moved.
