# Contributing to PlayGuard

Thanks for helping! This file covers building, testing, the code layout, releases and translations. For what the app does, see the [README](README.md); for what to work on, the [roadmap](ROADMAP.md). Everyone taking part follows the [code of conduct](CODE_OF_CONDUCT.md); for help rather than a change, see [SUPPORT.md](.github/SUPPORT.md).

## No code needed

Two minutes, if your console is still linked to the phone app: *PIN › Before unlinking: help decode…* saves the play-timer block, you change one setting in the phone app ("alarm only", or a bedtime for one day), and PlayGuard lists what changed. Attach that file to an issue: it is the data the [roadmap](ROADMAP.md#waiting-on-data-from-a-console) waits for most. Translation fixes from native speakers are just as welcome (see [Translating PlayGuard](#translating-playguard)).

## Build from source

| Command | What it does | Needs |
|---|---|---|
| `make test` | Host unit tests of the C service layer and of the UI-free C++ helpers and flow logic, with ASan + UBSan (`SAN=` to turn them off); the suites run in parallel, all of them even when one fails | gcc and g++ with the sanitizers, zlib headers, the borealis submodule — no devkitPro |
| `make desktop` | The real UI on Linux, against a simulated console | GLFW / X11 / D-Bus dev packages |
| `make web` | The same in a browser: `build-web/simulator/` (`make web-serve` serves it at localhost:8000) | Emscripten (`source <emsdk>/emsdk_env.sh`) |
| `make` | `./playguard.nro` — drawn with deko3d (`GL=1` for OpenGL) | devkitPro `switch-dev`, `DEVKITPRO` set |
| `make dist` | `./playguard.zip` (SD-card layout) | as above |
| `make dist-rescue` | `./playguard-rescue.zip`, the optional recovery sysmodule (`make` also builds it and bundles it in the romfs, for *Console › Optional modules*) | as above |
| `make dist-agent` | `./playguard-agent.zip`, the optional remote-link agent (bundled the same way) | as above |
| `./run.sh [ip]` | Builds in the `devkitpro/devkita64` Docker image, at the digest CI uses (read from `build.yml`), optionally `nxlink`s to a console | Docker |

Clone with submodules (`git clone --recursive`, or `git submodule update --init`): borealis is pinned at `extern/borealis/`. The fixes PlayGuard needs in it before upstream has them are patches in `patches/borealis/` (its README says why each one), applied to the submodule when CMake configures. `.gitmodules` says `ignore = dirty`, so `git status` leaves those changes out (a new borealis commit still shows); `git -C extern/borealis diff` shows them.

## The desktop simulator

`make desktop` runs the real borealis UI against `source/sim/`, a simulated console. Environment knobs (a flag is on with any value but empty, `0`, `false`, `off` or `no`; a number out of range is brought within it):

| Variable | Simulates |
|---|---|
| `PLAYGUARD_SIM_FW=20.5.0` | Another firmware (default 23.0.1, the newest verified on a console; above it, the firmware screen) |
| `PLAYGUARD_SIM_NO_CFW=1` | No Atmosphère |
| `PLAYGUARD_SIM_NOT_SET_UP=1` | Parental controls never set up (no PIN) |
| `PLAYGUARD_SIM_TIMER_OFF=1` | No play-time limit |
| `PLAYGUARD_SIM_RESTRICTED=1` | Today's limit reached |
| `PLAYGUARD_SIM_ALARM_ONLY=1` | *When the time is up* on a warning only: past the limit, the console does not restrict and the time left reads below 0 |
| `PLAYGUARD_SIM_NOT_COUNTING=1` | The time left not going down (a clock set back): *Today* says the console is not counting after 90 s on screen |
| `PLAYGUARD_SIM_STALL_S=20` | With `PLAYGUARD_SIM_NOT_COUNTING`: *Today* says so after that many seconds on screen instead of 90 (the smoke test's `outside` scenario) |
| `PLAYGUARD_SIM_TAB_RACE=1` | A read of the play data ending as each tab opens, the tab it replaces not freed yet (the smoke test's `alarm` scenario): the header's pill must still be the new tab's |
| `PLAYGUARD_SIM_UNLOCKED=1` | Parental controls temporarily unlocked |
| `PLAYGUARD_SIM_UNPAIRED=1` | No companion app linked |
| `PLAYGUARD_SIM_ALARM_OFF=1` | The "time's up" alarm off |
| `PLAYGUARD_SIM_ACCURATE=1` | An accurate network clock |
| `PLAYGUARD_SIM_AUTOSYNC_OFF=1` | *Synchronise Clock via Internet* off |
| `PLAYGUARD_SIM_NETWORK_OFFSET=1411` | A network clock that many seconds ahead of the console clock until it is set (the console clock follows it while *Synchronise* is on) |
| `PLAYGUARD_SIM_NTP=offline` | No time server answers (a console without Internet) |
| `PLAYGUARD_SIM_FAIL=timer,clock,unverified,bedtime,remove,launch,verify,forwarder` | Failures: the play-timer write, setting the clock, an unlock the system does not confirm, a bedtime the console does not take, removing a game or a content, resetting a launch version, the integrity check, installing or removing a forwarder (*Console › Forwarders*) |
| `PLAYGUARD_SIM_CHECK_MS=150` | How long checking one installed game takes (*Console › Check the installed games*) |
| `PLAYGUARD_SIM_GAMES_OK=1` | Every installed game fine (*Console › Check the installed games*; by default one of each problem) |
| `PLAYGUARD_SIM_SD_FREE_MB=300` | The SD card's free space, in MB (unset: unknown, as the desktop's own disk says nothing of a console; under 500 MB, *The SD card is almost full* on the Console tab) |
| `PLAYGUARD_SIM_EMUMMC=1` | Running on emuMMC |
| `PLAYGUARD_SIM_BLANK=1` | Atmosphère blanking the serial number |
| `PLAYGUARD_SIM_APPLET=1` | Applet (album) mode |
| `PLAYGUARD_SIM_NO_GAME=1` | No game open (applet mode with nothing behind it): no "game left open keeps counting" line, no "the game in progress is suspended" warning |
| `PLAYGUARD_SIM_DOCKED=1` | The console on its dock: *Text size › Automatic* draws the larger text |
| `PLAYGUARD_SIM_BATTERY=1` | The console on its battery (no charger): *Visual effects › Lighter on battery* leaves out the glow, the ring's pulse and its arc's animation |
| `PLAYGUARD_SIM_LEFT_MIN=4` | That many minutes left today while the timer counts (the child screen's last minutes) |
| `PLAYGUARD_SIM_NO_PDM=1` | No activity log |
| `PLAYGUARD_SIM_NO_PLAY=1` | Nothing played for weeks (the all-time totals stay): the Activity tab's empty state |
| `PLAYGUARD_SIM_GAMES=200` | That many more games played this week (a large library) |
| `PLAYGUARD_SIM_IDLE=1` | No game running |
| `PLAYGUARD_SIM_SKIP=900` | The console's time that many seconds later, a game played all along (unless `IDLE`): the time left goes down by as much, to the limit and past it, and the Activity tab counts it on the first game (read at each call: the web page's time buttons move it while PlayGuard runs) |
| `PLAYGUARD_SIM_ACCOUNTS=5` | That many user accounts, 0 to 8 (default 2: Alice and Léo), each playing twice as much as the next |
| `PLAYGUARD_SIM_KEEP=1` | The simulated console's settings (PIN, limits, bedtime, clocks) and what *Console › Check the installed games* changed (removed games, launch versions reset) kept in `playguard_data/sim_console.bin` from one run to the next; the variables that set its starting state then count for the first run only |
| `PLAYGUARD_SIM_BACKGROUND=1` | PlayGuard out of focus |
| `PLAYGUARD_SIM_REGION=2` | The console region |
| `PLAYGUARD_SIM_LATEST=1.1.0:24.0.0` | The latest release and the newest firmware it supports, for the update check (`offline` for no network) |
| `PLAYGUARD_SIM_SYS_LATEST=1.12.1:6.5.4:23.0.1` | The latest Atmosphère, hekate and firmware the daily update check finds (Atmosphère : hekate : firmware; `offline` for no network) |
| `PLAYGUARD_SIM_SYS_NOTES=<folder>` | What GitHub and switchbrew return for the release notes in *Console*: `atmosphere.json` and `hekate.json` (GitHub's release lists), `System_Versions.wiki` and `<version>.wiki` (switchbrew's pages, as wikitext); `offline` for no network |
| `PLAYGUARD_SIM_PASTE=https://gist.github.com/u/ab12` | What GitHub answers to *Send a report online* (`offline` for no network) |
| `PLAYGUARD_SIM_DEV_BUILDS=<folder>` | What the GitHub API returns for *Install another build*: `releases.json` (the releases tab), `latest.json` (the latest release, for *Update in place*), `artifacts.json`, `pulls.json`; `runs.json`, and for *Find a build* `pull_<n>.json`, `commit.json`, `run_artifacts.json`; `https://<local path>` download URLs are copied from disk (`offline` for no network); `PLAYGUARD_SIM_DEV_BUILDS_DELAY=<ms>` slows each answer |
| `PLAYGUARD_SIM_BOOT_CHOICE=a` | The answer of the start-up screen that offers the previous build after a start that did not finish (`a`: A, else B) |
| `PLAYGUARD_SIM_GITHUB_LOGIN=ok` | The GitHub device flow of *GitHub account*: `ok` approves at once, `denied` refuses, `offline` fails |
| `PLAYGUARD_SIM_HBLOADER=1` | A homebrew loader that can hand an update over to a store |
| `PLAYGUARD_SIM_NOW=<POSIX seconds>` | A frozen console time (with `TZ=` for its time zone) |
| `PLAYGUARD_SIM_STILL_FOCUS=1` | Not the console: the focus highlight without its moving glow, and the loading screen's ring still, for screenshots that compare |
| `PLAYGUARD_SIM_VERSION=1.0.0:1a2b3c4` | Not the console: the version and commit the header's badge shows (`1.0.0:` for a release), not the build's own, for screenshots that compare |
| `PLAYGUARD_SIM_HOLD_LOADING=1` | Not the console: the start-up stops on the loading screen, at its last step (the `loading` smoke scenario's screenshot) |
| `PLAYGUARD_SIM_CADRAN_NOGLOW=1` | Not the console: no background glow (`PLAYGUARD_SIM_CADRAN_NORING=1`: no ring on Today), the two custom draws of the look after the design boards (`source/view/cadran_*.cpp`: the rail's icons, today's ring, the figures in Sora from `resources/font/`, OFL), to weigh them |
| `PLAYGUARD_SIM_CUT_TEXT=1` | Not the console: once a second, every label the screen on top cuts short ("…") goes to `cut_text.txt` in the working directory with the screen's name, once each (`tools/cut_text_check.py`) |
| `PLAYGUARD_SIM_STATS=<file>` | Not the console: one line per frame (frame time with the FPS limiter off; nanovg's draw calls and triangles with `tools/perf_nanovg_stats.patch`), see `tools/perf_frames.sh`. On the console (and the desktop), *About › Help & diagnostics › Developer › Frame statistics* writes one line per second to `logs/frame_stats.txt` instead: the mode (docked, handheld), the UI thread's own time per frame and the late frames (`source/action/frame_stats_flow.cpp`) |
| `PLAYGUARD_SIM_MODULES=agent:running` | Optional modules running at start (`name:running`, comma-separated); a module starts only when its `exefs.nsp` is on the simulated SD card |
| `PLAYGUARD_SIM_AGENT=running` | The agent sysmodule runs while its simulated module does (`PLAYGUARD_SIM_MODULES=agent:running`): an agent simulated in the process, with its own command dispatch (`sysmodule/agent/source/agent_core.c`), to which PlayGuard hands the link; what it pushes and answers is logged as `sim agent: …`. An installed `exefs.nsp` holding `old agent` speaks another protocol, one holding `broken agent` never answers |
| `PLAYGUARD_SIM_AGENT_ORDER=limit_uniform=90` | An order the simulated agent hands PlayGuard once, after `Hello` |
| `PLAYGUARD_SIM_BUNDLED=<folder>` | The optional modules PlayGuard carries (`<name>/exefs.nsp` and `version.txt`, as `cmake/bundle_sysmodules.cmake` writes them in the romfs) |

Game patches are read from `./playguard_data/sd/`, the simulated SD card root; *Console › Forwarders* writes a few made-up homebrew there (`switch/*.nro`, `source/sim/sim_forwarder.cpp`) to make forwarders for.

### In a browser

The same simulator runs in a browser, with these variables in the URL (`?unlocked=1&fw=20.5.0`) and a panel to change them: [main's](https://playguard.link/simulator/), on PlayGuard's website, and each pull request's, linked in a comment on it. See [`web/README.md`](web/README.md). The page is in the console's 15 languages, the browser's unless the URL says `lang=`, with an *Auto* / *Light* / *Dark* theme, and PlayGuard starts in both. A new `PLAYGUARD_SIM_*` variable needs its entry in `web/params.json` and its label in `web/i18n/en-US.json` (`tools/check_web_params.py` fails CI without them); the other catalogs show the English one until they have theirs. Read it with `sim_env_flag()`, `sim_env_int()` or, for a text, `sim_env()` (`source/core/sim_env.h`), never `getenv()`: the web page's live changes go there, and it is unset on the console. Describe it in the table above too (the same check fails without it). Mark it `"live": true` when PlayGuard reads it at each use (not once at start-up): the page then changes it without a restart. The check fails on `live` for a variable read once only: into a static, or into the simulated console's first state (`sim_defaults()`, `source/sim/sim_state.c`). CI opens the build in headless Chromium (`tools/web_smoke.py`), and the pull request's comment shows its screens.

## Tests and CI

- `make test` — host unit tests (`tests/`, see [`tests/README.md`](tests/README.md)), including the recovery sysmodule logic (`tests/rescue/`), the remote link (`tests/sync_*`) and the agent (`tests/agent/`); every suite runs, in parallel, and leaves its output in `build/host-tests/<suite>.log`.
- `make check` — `make test`, then the resource check, the remote link's JSON documents (`tools/check_sync_json.py`) and `compat.json`.
- `tools/desktop_smoke.py <out-dir> [games|gate|errors|rescue|forged|lock|loading|devbuild|update|library|rollback|outside|alarm|sysnotes|cadran|cadranstates|cadranunlocked|cadranlarge|forwarders|sync|sync-311|agent|agent-update|agent-rollback|modules]` — clicks through every screen of the desktop build headlessly (needs `DISPLAY`, `xdotool`, ImageMagick) and saves screenshots. With no scenario it opens every tab, the Play timer's editors, the settings backup and the change history; `games` is the rest of that tour, run on its own so CI can run both side by side: a report sent online, *Console › Check the installed games* with every fix, check and removal, then *Activity › All games* and the PDF export. The `gate` scenario covers the firmware screen and developer mode on a simulated 24.0.0; `errors` covers a failed unlock and an unsettable clock; `rescue` the recovery screen, then quitting while still unlocked; `forged` a rescue report the console does not confirm (no action, the lock screen first); `lock` the lock screen of *Protect PlayGuard with the PIN › To open PlayGuard*; `loading` the loading screen, the start-up held at its last step; `library` a large library in *Activity › All games* (its first 50 covers, then *Show every game*, then the list); `devbuild` signing in to a simulated GitHub and installing a pull request's build in place out of its artifact; `update` a newer release found at start-up by *Check for updates every day*, postponed, shown again by *About › Check for updates*, then installed in place; `rollback` a build installed in place whose start never reached its first screen: the start-up offers the build before it, and A takes it back; `alarm` *Today* and the Play timer tab past the limit while the console only warns; `sysnotes` the release notes of the firmware, Atmosphère and hekate from *Console*, against a simulated GitHub and switchbrew. `cadran` tours the boards on top of the tabs: every tab, the child screen and back with the PIN, a day of the week edited with the stick and saved, a restriction level's confirmation, the text size, the network clock and a game's screen from its card; `cadranstates` its Today and Play timer past the limit (a warning only) with changes made outside PlayGuard; `cadranunlocked` the same two while parental controls are temporarily unlocked (*Turn back on* first, the header's pill saying so), in the light theme (every other scenario draws the default, dark one); `cadranlarge` Today, the Play timer, Activity and the child screen with *Preferences › Text size › Larger*, as on a TV. `outside` *Today*'s notices: changes made outside PlayGuard (a play time that started over, the clock, the limits) and, after 90 s on screen, a console that is not counting play time (it takes about two minutes). `sync` the remote link against a local Mosquitto (needs `mosquitto` and `mosquitto-clients`): what it publishes, an order applied and one refused, Home Assistant restarting, and `offline` at exit (`sync-311` the same in MQTT 3.1.1); `agent` the link handed to a simulated agent sysmodule; `agent-update` / `agent-rollback` updating that agent from PlayGuard, and putting the previous one back when the new one does not answer; `modules` installing, turning off at boot and removing the recovery module.
- `tools/cut_text_check.py <out-dir> [language …]` — starts the desktop build on the tabs in each of the 15 languages, at the normal text size and the larger one, and fails on any text cut short (drawn with "…"; borealis patch `0008`, `PLAYGUARD_SIM_CUT_TEXT`) that `tests/cut_text/allowed.txt` does not list. About 15 s a language and size; CI's `languages-1` to `languages-3` shards run it, five languages each (needs `DISPLAY` and `xdotool`).
- `tools/visual_check.py` — compares those screenshots with the references in `tests/visual/`. A screen that changed fails CI; see [`tests/visual/README.md`](tests/visual/README.md) to update them.
- `tools/smoke_all.py <out-dir> [-j N] [--update]` — runs every smoke scenario (the default one, `smoke`, and each one `desktop_smoke.py` tests for), N at a time (3 by default), each with its own display and D-Bus session (`xvfb-run -a … dbus-run-session`), into `<out-dir>/<scenario>/`; then the visual check of each one that has references, and a summary: each scenario, whether it passed, and the screens that changed. It fails on a failed scenario or a changed screen; `--update` replaces the references of the screens that changed instead. `--dry-run` lists the scenarios and their commands. Needs `make desktop` first.
- `tools/perf_frames.sh <name> [VAR=value …]` — the per-frame cost of one screen of the desktop build, headlessly (same needs as the smoke test, plus `dbus-run-session`): the median and p95 frame time over the steady state, and nanovg's draw calls and triangles once `tools/perf_nanovg_stats.patch` is applied in `extern/borealis` (`git -C extern/borealis apply ../../tools/perf_nanovg_stats.patch`; a local patch, never committed). `PERF_KEYS="Down Right"` presses keys first to reach another screen (xdotool names; Return is A, Escape B), `PERF_THEME=light` runs the light variant. Software GL rasterises on the CPU, so the figures weigh pixels far more than the console's GPU does: compare screens with each other, not with the console.
- `python3 tools/check_resources.py .` — checks the XML layouts and translation catalogs.
- `python3 tools/build_site.py <out-dir>` — builds the website (`site/README.md`); CI's `web` workflow builds it with the simulator for every pull request and `pages` publishes it. `node tools/site_screenshots.mjs <simulator> <out-dir>` takes its screenshots in each language from the web simulator.
- `node --test tests/web_page/*.test.js` — the web simulator's page logic (`web/sim_logic.js`).
- `python3 tools/check_web_params.py .` — checks that the web simulator's panel (`web/params.json`) and the table above have every `PLAYGUARD_SIM_*` variable, and that none read once only is marked `live`.

CI (`.github/workflows/build.yml`) runs all of the above plus the Switch build, the smoke scenarios in parallel shards (the desktop build made once, in `desktop-build`, and handed to them), on every pull request, every push to main and once a week. A pull request runs only the jobs its files need (the `changes` job): documentation, the website, the web simulator's page or other workflows only, the host tests and the resource checks; the host tests' suites only (`tests/` but `tests/visual/` and `tests/cut_text/`), no desktop build or smoke test; the smoke test's references or scripts only, no clang and coverage host tests; nothing the Switch reads (`tests/`, `source/sim/`, the smoke test's scripts), no Switch build. The visual check compares the sets in `tests/visual/` and fails on a changed screen (the simulator keeps the console time and the focus highlight still, so the screens come out the same in every run). The desktop and Switch builds turn PlayGuard's compiler warnings into errors (`make desktop CMAKE_ARGS=-DPLAYGUARD_WERROR=ON`, `make dist CMAKE_ARGS=-DPLAYGUARD_WERROR=ON`), and a compiler message is annotated on its line of the pull request; the Switch job also fails on a libnx older than 4.12.0 or an `.nro` without libnx's `LNY2` marker (`tools/check_nro.py`), and, outside pull requests (main, a release, the weekly run), checks that a second build gives byte-identical zips; `check_resources.py` warns about sentences a catalog still has in English.

Each job writes a summary on the run page (`tools/ci_summary.py`): what is being built, the suites, the coverage per file, each smoke scenario with its visual check and its time, and for the Switch build the `.nro` size against main's last build, what makes it big (from the linker map: `python3 tools/ci_summary.py map build/borealis.map --nro playguard.nro` shows the same table for a local build), the toolchain and the downloads. A run's artifacts are named after its build, `playguard-<version>-<ref>-<commit>-<component>` (`1.0.0-pr92-1f0a059`, `1.0.0-main-2bd4996`): `-nro` (the app, what the developer tools download), `-rescue` (the recovery sysmodule, as the zip and the raw `.nsp`), `-linker-map`, `-screenshots-<shard>` (with a contact sheet per scenario), and on a release build `-sdcard` (the store zip). The runner image is pinned (`ubuntu-26.04`): the references of the visual check were drawn by its mesa, so moving to the next image is a pull request of its own. The devkitPro image is pinned by digest in `build.yml`; `toolchain-watch.yml` opens an issue once a month when Docker Hub's `latest` moved.

## Code layout

| Path | Content |
|---|---|
| `source/core/` | C, libnx: `pctl_ops` (and `pctl_dump`, the pctl part of the diagnostic report), `time_ops`, `sysinfo`, `playstats` (its service-free part in `playstats_logic`), `gamecheck` (its rules in `gamecheck_rules`, shared with the simulator), `forwarder` (NRO forwarders on the HOME menu; their contents built by `forwarder_pack`, which needs no console), `nacp` (a game's name out of its control data, for both; `nacp_read` reads it on the console), `platform`, `rescue`, `pure`, `calendar`, `write_guard` (these last four need no console and are shared with the simulator), `modules_nx` (start / stop a sysmodule), `startup_hook` (times borealis' `userAppInit`, which libnx calls before `main`), `crash_handler` (PlayGuard's CPU exceptions to a crash file, before Atmosphère's report) |
| `source/tab/` | One class per tab (`dashboard_tab` is *Today*, `security_tab` the PIN tab), and the two screens opened from one: the network clock (from Console) and Help & diagnostics (from About), shown with `ui::open_screen`; `tab_base` is what they share |
| `source/action/` | Flows, one per thing a tab does, with their UI-free logic in `*_logic.cpp` where there is one: the play-timer write and its recorder, the clock (and a console no time server answers), the PIN prompt and the console lock, settings backups and restores, the change history and undo, changes seen outside PlayGuard and timer health, the notification bell, the firmware screen, the recovery screen, reports and sending them online, updates, GitHub sign-in and development builds, the SD-card write queue, clearing the cache and the log files, the remote link (`sync_flow`, `sync_orders`) and the agent's update (`agent_update`) |
| `source/activity/` | Screens: per-day editor, the Play timer's *Advanced*, profiles, all games (a list or covers) and a game, the check of the installed games, the forwarders, the release notes of Atmosphère, hekate and the firmware, first steps, change history, the notifications, firmware, recovery, the lock screen, the diagnostic report, what's new and the full changelog, the start-up error, the update screen, the development builds and a build's page, *Remote access* and *Optional modules*, the loading screen (the start-up runs one step per frame under it; the intro keeps it 2 s) |

| `source/ui/` | The Cadran look: the palettes, header and rail (`cadran_frame`), the pieces every screen builds with (`cadran_kit`), dialogs, pickers and the duration picker (`cadran_modal`); dialogs, formatting, the colours the palettes leave out, the text size and the visual effects, the console's state as text, read-only greying and visibility |

| `source/sim/` | The simulated console for the desktop build (`sim_state.h` says which file stands in for which service, and the rules of its lock; the made-up games in one table, `sim_games.c`; `sim_platform.cpp`) and its simulated network (`sim_net`, which the `util/*_net.cpp` files read; `web_http` answers every request offline in a browser) |

## Pull requests and releases

Releases are automated with [release-please](https://github.com/googleapis/release-please), which reads [conventional commits](https://www.conventionalcommits.org/):

- Give each pull request a conventional title with a scope, the part of the app it changes (`feat(history): …`, `fix(play-timer): …`, `docs(install): …`, `feat(notices)!: …` for a breaking change); CI checks it. release-please sorts each section of the changelog by scope, so a title without one lands apart from the rest.
- **Squash-merge** pull requests, so each one lands as a single commit carrying that title. A plain merge commit makes release-please apply a PR's `BEGIN_COMMIT_OVERRIDE` block to every commit of the PR.
- release-please keeps a `chore(main): release X.Y.Z` PR open; merging it tags the release and attaches the `.nro` / `.zip`.
- release-please runs with a token of the *PlayGuard Release* GitHub App (variable `RELEASE_APP_ID`, secret `RELEASE_APP_PRIVATE_KEY`; permissions Contents, Pull requests and Issues: write), not `GITHUB_TOKEN`: the app is on the tag ruleset's bypass list, so it can create the `vX.Y.Z` tag, and its pushes to the release PR run the required checks.
- **The release page** is laid out by the release job: a summary (`.github/release-notes/X.Y.Z.md`, merged before the release PR; else, with an `OPENROUTER_API_KEY` secret, one written by a language model), the figures, the commit list folded (users, then contributors), the screens that changed, the install section, the build report, and a discussion. [`.github/release-notes/README.md`](.github/release-notes/README.md) says how; *release-page* in Actions does it again for an existing release.

**Development builds:** nothing is published for them. The developer tools install the `playguard-<version>-<ref>-<commit>-nro` artifact of a build run (a zip holding `playguard.nro`; the artifacts API only filters by an exact name, so the app lists a few pages of a run's artifacts and keeps that one): main's last commits and the newest run of each open pull request from a branch of this repository; pull requests from forks are left out, as their code is not reviewed yet (`source/util/dev_builds.hpp`, [SECURITY.md](SECURITY.md)). GitHub hands artifacts to signed-in users only, hence the GitHub sign-in (device flow, GitHub App client ID in `source/util/github_auth.hpp`; with the Device Flow enabled and token expiry off; the app's only permissions are Actions: read and Gists: write). For a pull request, `PLAYGUARD_COMMIT` makes the app report its head commit, as the artifacts API names the run. Every build but a release one (`PLAYGUARD_RELEASE=1`, set for the `vX.Y.Z` tag's build) shows itself as a development build in the header, at the right: an amber **DEV** tag, the version and the commit, where a release shows a plain grey `v1.2.0` (`source/view/version_badge.hpp`).

Each release also publishes `compat.json` (`tools/gen_compat.py`: the version and the newest checked firmware), which the app's update check reads, plus `build-info.txt` and `SHA256SUMS.txt`. Details in [`packaging/README.md`](packaging/README.md). The `.nro`, both `.zip` and `compat.json` also carry a [build provenance attestation](https://docs.github.com/actions/security-for-github-actions/using-artifact-attestations): `gh attestation verify playguard.nro -R JigSawFr/PlayGuard` checks that a download was built by this repository's CI.

**Reproducible zips:** `make dist` and `make dist-rescue` give every file in the zip the date `SOURCE_DATE_EPOCH` (POSIX seconds; default: the last commit's time, `git log -1 --format=%ct`) and add the files in a fixed order without extra attributes, so the same commit and `.nro` give a byte-identical zip. The deko3d shaders are not compiled at build time (uam does not always give the same bytes): `shaders/` keeps them, with the checksums of the borealis GLSL they come from, and configure stops when that GLSL changes; then rebuild them with `-DPLAYGUARD_UAM=ON`, copy `build/dksh/*.dksh` to `shaders/` and update `shaders/glsl.sha256`. Set `SOURCE_DATE_EPOCH=<seconds>` to rebuild one from another checkout. CI builds the zips twice and compares them on main, for a release and once a week; when they differ, `tools/repro_diff.py` says where (a zip entry, a segment of the `.nro`, a RomFS file, a shader) and the run keeps both builds as an artifact.

When a change is visible to users, update the English and French pages **both**. The READMEs ([README.md](README.md), [README.fr.md](README.fr.md)) stay short (about one screen): the pitch, features, compatibility, install, quick start and links; the details go to the user guide in [`docs/`](docs/) — `getting-started.md` (the walk-through and the everyday tasks, a parent's first page), `features.md` (every tab and setting), `install.md`, `compatibility.md`, `troubleshooting.md` (locked out, the common problems, reporting a bug) — with its French version in [`docs/fr/`](docs/fr/) and the console's other languages in `docs/<language>/`. Those other translations may lag: after changing an English page, stamp the French one again (`python3 tools/doc_stamp.py docs/fr/<page>.md`); `python3 tools/doc_delta.py docs/<language>/<page>.md` shows what changed in the English page since its translation was stamped (the diff from the version the stamp names), and `--all` lists every translation that is behind; the others say on the website that the English page may be more recent until someone updates and stamps them. `python3 tools/check_site_links.py <site-dir>` checks every link of a built site (CI runs it). `tools/site_layout.py <site-dir>` (Playwright) checks its layout on a phone, a tablet and a desktop, and with `SITE_AXE=<axe-core's axe.min.js>` its accessibility (CI runs both for a pull request that changes the site). The reference pages (`config.md`, `parental-controls.md`, `companion-app.md`) are in English only.

## Translating PlayGuard

PlayGuard is translated into every language the console offers: English, French (France and Canada), German, Spanish (Spain and Latin America), Italian, Dutch, Portuguese (Portugal and Brazil), Russian, Japanese, Korean and Chinese (simplified and traditional). It follows the console's language unless *Preferences › Language* picks another one. British English consoles get the English strings, already in British spelling (`CMakeLists.txt` copies them under `en-GB`). Fixes from native speakers are welcome.

To add a language:

1. Copy `resources/i18n/en-US/playguard.json` to `resources/i18n/<code>/playguard.json` (`<code>` as the console names its language, see `brls::LOCALE_*`) and translate the values. Keep every key, and as many `{}` placeholders as the English text, in the same order.
2. Add `<code>` to `config::LANGUAGES` in `source/util/config.hpp` (the language picker and the saved preference use that list).
3. Add the language's own name under `"tools" › "languages"` in **every** `playguard.json` (`"ru": "Русский"`). A regional variant (`fr-CA`, `es-419`, `pt-BR`) is a full catalog of its own: borealis falls back to English, not to the base language.
4. Optionally add `resources/i18n/<code>/hints.json` for borealis' button hints when borealis has none for that language (see `resources/i18n/fr/hints.json`); missing strings fall back to English.
5. Run `python3 tools/check_resources.py .`: it reports missing or extra keys, placeholder mismatches and a language missing from the picker. CI runs the same check.
