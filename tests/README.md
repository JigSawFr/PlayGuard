# Host tests

Plain-gcc unit tests of the C service layer and of the UI-free C++ helpers.
The C suites compile the real source against a small fake `<switch.h>`
(`-DNX_HOST_TEST`) that models service ownership, firmware version, command
payloads and buffer descriptors — not Horizon IPC encoding.

```sh
make test
```

It needs gcc and g++ with AddressSanitizer and UndefinedBehaviorSanitizer
(`SAN=` turns them off), the zlib headers (`zlib1g-dev`, for `playstats` and
`dev_builds`), and the borealis submodule (`git submodule update --init`) for
nlohmann/json: `make test` says so when it is missing. `make test CC=clang
CXX=clang++` builds them with clang (its sanitizer runtime: `libclang-rt-dev`);
`make test SAN= COV=--coverage` with gcc leaves the `.gcda` files for `gcovr`
in `build/host-tests/`. CI runs all three.

The web simulator's page logic (`web/sim_logic.js`) is tested with Node
instead, in `web_page/`: `node --test tests/web_page/*.test.js` (CI runs it
with the resource checks).

The suites build and run in parallel (`JOBS=n` for fewer jobs), every one of
them even when one fails: each leaves its output in `build/host-tests/<suite>.log`
and a `<suite>.ok` when it passed, and `make` fails at the end if any did. A
suite is three variables in the Makefile (`<name>_SRC`, `<name>_FLAGS`, an
optional `<name>_LIBS`); a new one is three lines there, next to the others.
A C++ suite leaves out `<name>_FLAGS` when `TEST_CXXFLAGS` (C++20, `source/`
and borealis' headers) is all it needs, so it is often one line. A C++ suite
that needs C sources names them in `<name>_CSRC` (with `<name>_CFLAGS`): each
is built by `$(CC)` and linked in, as clang++ refuses to build a `.c` file as
C++. One that links `source/util/date.cpp` gets `source/core/calendar.c` that
way without naming it.
One more when a suite needs it: `<name>_ARGS`, what the program is run with
(`sync_core` writes its documents to `build/host-tests/sync/`).

The suites check with `CHECK(expr)` from [`check.h`](check.h), not `assert()`:
the expression is always evaluated (also under `-DNDEBUG`), a failure prints
file:line and the expression and the suite goes on, and `main()` ends with
`return CHECK_DONE("... passed");`, non-zero when any check failed.
`if (!CHECK(p)) return;` stops a test whose next line needs `p`; `REQUIRE(expr)`
stops the program (a mock handed a bad pointer, a setup step everything needs).

What the suites share, next to `check.h` (`-Itests`):
[`temp_dir.hpp`](temp_dir.hpp), a fresh folder under `/tmp` removed with
the object (`TempDir tmp("config", TempDir::Enter)` also makes it the
working directory, so `paths::data_dir()`, `./playguard_data` on the host,
lands in it, until `CHECK(tmp.remove())` or the end);
[`fs.hpp`](fs.hpp), the files a suite sets up and looks at (`fs::write`
with its folders, `fs::exists`, `fs::read` and `fs::content_of` as the app
reads a file, `.tmp` included); and
[`fake_switch_base.h`](fake_switch_base.h), what every fake `<switch.h>` of
the C suites starts with (libnx's integer types, `Result` and its macros,
the firmware version macros), each suite's own `switch.h` adding the
services its code calls.

## Fuzzing

`tests/fuzz/<target>/` holds a libFuzzer target for each parser of outside
data, built by clang with AddressSanitizer and UndefinedBehaviorSanitizer:

```sh
make fuzz                  # every target, 30 s each, in parallel (JOBS)
make fuzz FUZZ_SECONDS=300
make build/fuzz/markdown.run FUZZ_SECONDS=60   # one target
```

It needs clang and its fuzzer runtime (`libclang-rt-dev`). Each run starts
from the seed inputs in `tests/fuzz/<target>/corpus/` (never written to) and
keeps what it finds in `build/fuzz/<target>.corpus/`; its output is in
`build/fuzz/<target>.log`. A crash, a sanitizer report or a broken property
(`FUZZ_ASSERT`, [`fuzz/fuzz.h`](fuzz/fuzz.h)) stops the target and leaves
the input as `build/fuzz/<target>-crash-<sha1>`: `build/fuzz/<target> <that
file>` replays it. A target is a few lines in the Makefile (`<name>_FUZZ`,
next to the others); a `dict` file next to its corpus is passed as libFuzzer's
dictionary. CI runs every target for 30 s.

| Target | Fuzzes |
|---|---|
| `zip_read/` | `zip_read::extract()` on any archive (a downloaded Actions artifact): an extraction that succeeds leaves at most the size allowed, one that fails leaves no file and says why. |
| `markdown/` | `markdown::parse()`, `inline_text()` and `safe_text::clean()` on any bytes: the bounds `markdown.hpp` promises, every string valid UTF-8, `clean()` within its size and stable. |
| `changelog/` | `changelog::parse()` and `release_notes()`: the number of releases asked for kept, icons as hex code points. |
| `rescue/` | `rescue_request_mode()` and `rescue_report_parse()` (files anyone with the SD card can write): a parsed report formats back to the same, a refused one leaves the output untouched. |
| `config/` | `config::load()` of `config.json` and `state.json` (in a temporary folder): what it read saves and reads back to the same settings. |
| `game_cache/` | `game_cache::decode()`, then the rules of `core/gamecheck_rules.c` on what it returns, `to_check()`, `put()` and `set_verified()`: a decoded file encodes and decodes to the same, strings end in their arrays, the content count is bounded, every `bool` 0 or 1. |
| `play_cache/` | `play_cache::decode()` and `shift_days()`: the same round trip, games bounded, names ending in their arrays, every `bool` 0 or 1. |

The `pctl_session`, `time_ops` and `ntp_packet` suites started from anbingxi's
fork (`diag/fw22-5-readonly`). Passing them does not prove how a real console
behaves; `tools/desktop_smoke.py` exercises the UI, and hardware testing is
still required for firmware-specific behaviour. `visual/` holds the reference
screenshots CI compares the smoke test's screens with (`tools/visual_check.py`,
see `visual/README.md`).
